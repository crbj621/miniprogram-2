# 业务与算法规则

规则以服务端实现为准；前端隐藏不是权限验证的替代。

## 身份、模块与管理

- 学生身份以服务器 token 与 App 登录状态为准。保存资料成功后才提交登录；authVersion/sessionVersion 防止退出前请求回写。
- 五个模块键：running、food、canteen、forum、rider。服务端兼容旧布尔值和 run 键，规范写入 `{ enabled, name }`，部分更新不清空其他设置。
- 同学端读取公开模块配置，区分加载、失败、全部关闭。关闭模块隐藏入口和相关菜单；食堂服务端同步拒绝学生访问。
- 超级管理员且账号未禁用才可改开关；读取失败不能保存。快捷设置需点击保存才生效。
- 管理首页常用入口是模块、食堂、跑步、公告；其他事务折叠。管理权限仍由服务器验证。

## 跑步、组队与榜单

- GPS 距离结合精度、速度、时间、计步过滤静止抖动、跳点和折返噪声；保留有计步支持的真实转弯。GPS 与计步距离不重复加，解绑使用同一回调。
- 开始自动收起卡片；暂停展开；继续收起。运动中准备功能与底部导航隐藏，暂停 / 结束在卡片外保留。
- 失败或离线成绩存当前用户本机队列，用相同 clientRunId 重试，服务器成功后才清除。零距离不写假成绩；队伍结算必须等待成绩保存。
- 排名先完整汇总再取榜单前列，不能先截断 1000 条。相同里程保持稳定顺序，追赶距离不伪造。
- “搭子和情侣”榜沿用 couple 类型，只累计同一对成员关联队伍下的已保存成绩；普通多人队伍不混入。
- 组队资格、重复奖励和成绩保存使用服务端校验、事务及数据库锁。示例成绩由管理员明确生成，可从跑步管理移除；不能删除真实记录来保持空库。

## 点餐与骑手

- 真实菜品集合为 food_dish，小程序商家 / 管理员与学生读写同一份数据；不要恢复旧 food_menu 入口。库存 0 表示售罄。
- 订单状态采用 pending → processing → ready → completed；取消与配送另按服务端状态机验证。
- 订单、库存、优惠券、取消回退和骑手收入使用同一连接事务及行锁；业务失败也回滚，不使用吞异常的补偿。
- 金额按整数分计算。新人券固定 ID + 唯一插入，重复领取不覆盖已核销状态。店铺资料批量读取，避免 N+1。

## 独立食堂评价与投稿

- packageCanteen / canteen_reviews 与点餐 food_* 集合分开。档口、菜品、评价分别为 canteen_stalls、canteen_dishes、canteen_reviews。
- 每位学生每道菜一条 1–5 分评价，可编辑，不重复计人数。只统计可见评价；档口按已发布菜品的所有可见评价汇总。
- 至少两票且均分 ≥ 4 为推荐，至少两票且均分 ≤ 2.5 为避雷。无评价显示暂无评分。
- 优质随机先筛 ≥ 4 分且两票；全部随机抽已发布菜品；异食癖随机先筛 ≤ 2.5 分且两票。使用 crypto.randomInt 等概率抽候选，无候选显示空池。
- 评价按真实均分排序，同分再比较人数；未把贝叶斯调整分冒充实际得分。档口汇总一次按菜品归属分组。
- 管理员隐藏后，作者不能再次提交恢复；编辑与隐藏读取使用事务锁。草稿不对同学显示。
- 投稿先进入 canteen_submissions，管理员审核后才发布档口 / 菜品；不自动加评分，pending 只能处理一次。

## 校园动态

完整分区来自 forum 接口；栏下菜单选择后收起，新分区复位第一页。最新 / 热门与分页使用请求序号，旧响应不能覆盖新筛选；失败不跳过页码。私信与未读信息要求学生身份。

## 验证边界

12 组本机回归覆盖登录、模块、评分、事务请求、跑步交互 / 漂移、刷新竞态、榜单和每日主题。服务器真实 HTTP/SQL 与专项脚本在 server/scripts，运行前考虑真实用户；脚本会创建临时数据，部分会暂时改模块设置，应使用测试库或维护窗口。

已有接口与数据库回归不能证明真实微信登录、手机弱 GPS / 锁屏、照片上传或配送全流程完成，也不是完整安全审计。

## 校园跑当前实现（2026-10-02）

本节描述已实现的代码；后端已发布至 `20261002-023132`。先前“建议尚未实施”的检查记录已被当前规则替换。

### 根因与改造

旧实现按 accuracy 乘位移，导致同一约 20 米路段在 accuracy=65 时只记 10 米；距离又被反算成步数。结束弹框使用早先捕获的距离，活动状态只保存在内存，补传日期取收到当天。服务端接受零时长或极端速度，榜单先载入整个集合。

| --- | --- |
| 球面距离保留，不按精度给米数打折；accuracy >80、非法坐标、超过 15 秒采样间隔断段，不跨缺口补直线 | utils/run-metrics.ts、pages/index/index.ts |
| speed <0.6 且无新增脚步时忽略静止漂移；连续位移超过 12 m/s 或单段超过 180 米拒绝；无脚步的 A-B-A 回漂撤销上一段，有脚步的真实折返保留 | RunTracker |

以上前端源码路径相对 miniprogram。计步、步长和运动模式仍是估计，不是系统硬件计步器。超过 31 天的待传记录保留在本机，服务器拒绝保存并显示原因，不自动删除。

### 开源调研与选型

检索关键词：`GPS running accuracy JavaScript geolib`、`Kalman filter GPS JavaScript`、`Turf distance simplify`、`wechat-miniprogram getWeRunData`、`MariaDB generated virtual columns JSON index`。

- [geolib](https://github.com/manuelbieh/geolib)：地理距离函数候选；现有公式不是偏差根因，因此不额外引入。
- [KalmanJS](https://github.com/wouterbulten/kalmanjs)：一维噪声滤波参考，不能直接作为完整 GPS / 惯性融合；本次未引入，避免未经真实轨迹标定就削短弯道。
- [Turf](https://github.com/Turfjs/turf)：轨迹简化 / 地理围栏候选；本次仅限制绘图点数，不将简化轨迹用于计距。
- [微信官方示例](https://github.com/wechat-miniprogram/miniprogram-demo)与 [API 定义](https://github.com/wechat-miniprogram/api-typings)：登录、定位和微信运动接口依据。
- [MariaDB 虚拟列与索引](https://mariadb.com/docs/server/reference/sql-statements/data-definition/create/generated-columns)：沿用现有 MariaDB + mysql2 聚合，无新 ORM。

本次没有新增依赖；没有找到直接匹配且已核对的 SkillHub 技能，未安装社区脚本。

### 微信运动（日步数独立功能）

校园跑准备卡片新增“今日微信运动”。用户主动点击同步并允许 scope.werun 后，客户端刷新 wx.login，获得同一微信会话的 encryptedData/iv，提交 `/api/we-run`。服务端用 Node.js 自带 crypto 解密，核对用户、AppID、水印时间（15 分钟内）、日日期、重复日与非负整数步数，按用户与日期更新 `wechat_steps`。

JWT 只关联一个微信会话 ID；session_key 仅在服务器内存中保存 2 小时，重启后点击同步会重新登录，不返回给客户端、不写日志。不同设备 / 登录对应不同会话，避免互相覆盖。旧水印请求不能覆盖较新步数。维护目录的账号密钥仍按用户要求保存明文，微信接口数据解密与维护文件存储方式无关。

官方目前提供过去三十一天的按日数据，用户主动进入小程序时更新；本项目旧类型注释写三十天，以最新官方定义为准。今日无数据显示横线，不用昨天数据冒充。最近 31 日可返回接口，界面当前只显示今日与同步时间，没有额外新增日步数榜。

微信日步数包含当天其他活动，不能可靠地作为一次跑步的实时步数、配速、步频、精确补距或防作弊证据；不混入跑步统计、榜单或组队发券。
